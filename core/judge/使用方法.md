# 使用方法：判断接口

::STATE{@PART, name:judge, kind:core, external_apis:none, entry:core/judge/judge.py}
::STATE{@LAYERS, perception:"SOUL 本地规则 或 judgment 插件", decision:"f_v5 冻结 本地算"}

每个决策节点都走同一个接口：状态进，`{choice, judge:{v, mode, conf, reason}, mode_local}` 出。感知层把场景打成 11 维向量并选一个选项；决策层按 iLang v5 的 f_v5 把向量变成模式 M1 到 M8。**决策层不是 SOUL 的一部分，不是插件的一部分，是协议。**

## 七个节点与状态字段

| 节点 | 状态字段 | 选项 |
|---|---|---|
| offer.select | 选项各自的 data：epc、reversal_rate、cookie_days、ppc_allowed、category | offer id 加 none |
| lp.publish | lp_check_passed | publish、fix |
| campaign.launch | spec_valid、lp_published、account_status、daily_budget、max_cpc、is_new_account | go、hold |
| campaign.adjust | days_running、spend_total、spend_window、clicks、avg_cpc、conversions、commission、last_change_days、daily_budget | keep、bid_down、budget_up、budget_down、pause |
| keyword.action | clicks、conversions、avg_cpc、cost | keep、pause、bid_down、negative |
| conversion.upload | rows_in_window、rows_out_of_window、gclid_all_valid、reconciled | upload、hold |
| anomaly.escalate | account_status、disapprovals、spend_today、spend_avg_7d、identity_or_payment_verification_requested | continue、pause_all、escalate |

字段缺了 `cer` 就低，低过 0.30 变 M5（要信息，不动）。这是故意的。

## 模式怎么用

::RULE{M1或M2⇒执行|M3⇒只提议 进报告|M4⇒只建议|M5⇒缺信息 不动|M6⇒交本人|M7⇒换路|M8⇒停}
::RULE{aut低于0.55时M1_M2压成M3⇒动作超出config.caps就是这个效果 用户放宽caps才会执行}
::RULE{命中SOUL任一::BOUNDARY⇒M8 无论向量}

## 步骤

[STEP:1|自测|by:agent]

```bash
python3 core/judge/judge.py --selftest
```

[STEP:2|单点试判|by:agent]

```bash
python3 core/judge/judge.py --node campaign.adjust --state tests/fixtures/state.adjust.json --choices tests/fixtures/choices.adjust.json
```

stdout 是响应 JSON，stderr 是四行 `::JUDGE{v5.0}` 块。可以用正典校验器核：`python3 reference/ilang/ilang_judge_validator.py --check <存了那四行的文件>`。

[STEP:3|换提供者|by:human_then_agent]
`config.judgment.provider` 改成 `llm`、`jev` 或 `soul-api`，对应插件的环境变量放好。失败自动退回本地规则，响应里 `fallback:true`。

## 审计

每个判断的向量、模式、提供者都进 `runs/<id>/report.json` 的 `judgments`，教练要看就贴这个文件，与真实结果对照，用来校 Jev 与 SOUL。

::BOUNDARY{never:用提供者报的mode代替mode_local|scope:permanent}
