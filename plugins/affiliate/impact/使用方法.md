# 使用方法：Impact 联盟插件

::STATE{@PLUGIN, id:affiliate/impact, contract:plugins/affiliate/契约.md, sub_id_param:subId1, readback:SubId1, api:"api.impact.com/Mediapartners/{SID}/… 伙伴 API v16"}
::OBJECTIVE{id:impact|owner:user|trust:untrusted|version:1|status:active}
  target: 用本人 Impact 伙伴账号拉已加入项目与合同条款、生成带 token 的追踪链接、每天把佣金与撤销带回主干
  ACCEPT: 四个动作各跑通一次 AND Actions 里 SubId1 回读到主干发的 token
  NON_GOALS: 选 offer（那是主干 offer.select 节点的事）、申请项目（本人在 Marketplace 做，API 没有申请接口）、任何非本人账号

## 账号前提（本人做）

[STEP:0|伙伴账号|by:human]
本人真实身份注册 impact.com 伙伴（partner）账号，填本人税务信息（非美国人 W-8BEN），媒体资产填自己的域名。先加入 Marketplace（审核约三个工作日），再逐家申请品牌的项目；审核不过或所在国不接受，这条线判停，不换身份不注册新号。API 只看得见已加入的项目：一个项目都没加入时，offers 与 commissions 跑出来就是空的，这不是故障。

[STEP:0.1|API 凭据|by:human]
app.impact.com → 右上角头像 → Settings → Technical → API → Create Access Token。作用域只勾读权限：Campaigns、Contracts、Actions、Reports。Account SID 放环境变量 `IMPACT_ACCOUNT_SID`，Auth Token 放 `IMPACT_AUTH_TOKEN`；仓库与日志里不出现值。没勾 Contracts 的 token 也能跑，只是 offers 里的佣金率、锁定期、cookie 窗口为 null（实测回 403，插件按设计降级）。

## 四个动作

[STEP:1|offers 拉项目与合同条款|by:agent]

```bash
python3 plugins/affiliate/impact/offers.py --with-terms --out runs/<id>/offers.json
python3 plugins/affiliate/impact/offers.py --campaign-ids 4321,4322 --out runs/<id>/offers.json
```

`GET /Campaigns?InsertionOrderStatus=Active` 只列已加入的项目，只留 Type=Performance 且合同 Active 的；`GET /Contracts` 取佣金率（DefaultPayoutRate 或 DefaultPayout）、锁定期（Locking.Period）、cookie 窗口（ValidReferrals 里 CLICKS 的 Window 折成天）、币种，`--with-terms` 把特别条款原文带进 `terms_text`。`offer_ref` 形如 `impact:<AdvertiserId>:<CampaignId>`，`click_url` 是项目的 TrackingLink，开局的 offer 表直接用它。

::RULE{Impact伙伴API不给项目层面的EPC或转化率⇒epc与epc_3m一律null 不编数 选品第一条算不出来 开局第一轮由用户--pick定 跑起来后用partner_performance_by_program报表与自己的点击算}
::RULE{HasStandDownPolicy为true⇒brand_bidding_allowed为false 政策文件说true也不放行 那是品牌对竞价与商标的限制}
::RULE{Contracts回403⇒合同字段null stderr说明 不算失败 到token卡片里补Contracts读权限即可}

**PPC 政策 API 不给。** Agent 读 `--with-terms` 带出的 `terms_text`（合同特别条款原文）或后台该项目的条款，把核对过的值写进 `data/inbox/impact-offer-policy.json`（按 CampaignId 键：`ppc_allowed`、`brand_bidding_allowed`、`cookie_days`、`lock_days`、`allowed_traffic`、`reversal_rate`、`category`），再跑一次 offers。没核对就是 null，主干按不允许处理。

::RULE{条款写明不许PPC或不许品牌词⇒ppc_allowed或brand_bidding_allowed填false 不投}

[STEP:2|link 生成带 token 的链接|by:agent]

```bash
python3 plugins/affiliate/impact/link.py --base "https://brand-x.sjv.io/c/1234567/654321/4321" --token <token>
```

在追踪链接后追加 `subId1=<token>`，这是 Impact 官方写法，所有追踪链接都认，vanity 链接也认；已有 subId1（不分大小写）就替换，其他参数不动。subId1 上限 255 位字母数字，主干 20 位 token 稳稳装下。日常里这一步由自有域名的中转（`plugins/deploy/cloudflare`）在每次点击时自动做：`/go` 铸 token、存映射、302 到带 subId1 的链接；开局写 offer 表时参数名从本插件 manifest 的 `limits.sub_id_param` 取。

[STEP:3|commissions 拉佣金与撤销|by:agent]

```bash
python3 plugins/affiliate/impact/commissions.py --days 7 --out runs/<id>/commissions.json
```

`GET /Actions` 按最后更新时间开窗：StartDate 与 EndDate 必须成对，单次跨度不超过 45 天，脚本自动切段并翻 `@nextpageuri`。按更新时间而不是事件时间开窗，是为了让状态变化也落进窗口：一条早先追踪的 Action 这几天被撤销，它会再出现一次，State=REVERSED。PENDING ⇒ new，APPROVED ⇒ closed，`sub_id` 装 SubId1，`click_time` 装 ReferringDate（点击时间），`event_time` 装 EventDate。

Impact 没有负数的新记录：撤销是同一笔 Action 的 State 变成 REVERSED。这种只出一行拒付：event_id `<Id>:rev`，amount 为负，is_chargeback true，original_event_id 指向原 Id，event_time 取撤销时间；金额优先取同窗口 `GET /ActionUpdates?State=REVERSED` 里该 Action 的 DeltaPayout（负数），没有就取 Payout 或 IntendedPayout 的相反数。`offer_ref` 要 AdvertiserId，Actions 里只有 CampaignId，脚本先 `GET /Campaigns` 建一张对照表。

::RULE{REVERSED只出一行负额拒付 不出正数行⇒对账把status=reversed当拒付 正数会被灌成正向调整}
::RULE{日常循环只调commissions一个动作⇒拒付行必须随佣金一起出 chargebacks动作只是再筛一遍}

没有 API 时的退路：后台 Reports → Action Listing 导出 CSV，`--csv <file>`。表头别名在脚本的 `CSV_ALIASES`，还没对着真实导出核过。限速：/Actions 每小时 500 次，/ActionUpdates 1000 次，一天一轮用不到百分之一；超限 429 脚本按 Retry-After 退避一次。

[STEP:4|chargebacks 拒付解析|by:agent]

```bash
python3 plugins/affiliate/impact/chargebacks.py --commissions runs/<id>/commissions.json --out runs/<id>/chargebacks.json
python3 plugins/affiliate/impact/chargebacks.py --days 30 --out runs/<id>/chargebacks.json
```

从 commissions 的输出里筛 is_chargeback 行。Impact 的原事件 id 永远可知，`unlinked` 里只会是缺 ActionId 的坏数据，主干对它们记 unknown，不做负转化。

## EPC 从哪来

伙伴 API 不给任何项目层面的 EPC，Marketplace 页面给不给官方文档没写。跑起来以后用自己的数据算：`GET /Reports/partner_performance_by_program?START_DATE=YYYY-MM-DD&END_DATE=YYYY-MM-DD`（Performance by Brand）与 `partner_performance_by_subid`（Performance by Sub ID and Shared ID）给自己的点击、动作与收入，列名用 `GET /Reports/{Id}/MetaData` 查，每页固定 20000 行，/Reports 每小时 250 次。接进判断是下一版的事；这一版 epc 留 null。

## 实测记录

2026-10-20 用真实伙伴凭据只读跑通四个动作（全部 GET，没有写任何东西）。认证通；Campaigns、Actions、ActionUpdates、Reports 回 200，限速头 X-RateLimit-Limit-hour 分别 1000、500、1000、250，与文档一致。账号零个已加入项目：`offers --with-terms` 出 0 行并在 stderr 提示去 Marketplace 申请；`commissions --days 7` 与 `chargebacks --days 7` 各 0 行，StartDate/EndDate 的 ISO 8601 写法被接受；`link` 用样例 TrackingLink 装上 subId1。Contracts、Ads、Deals 回 403 {"status":403,"title":"Access Denied"}，是 token 没勾这几项作用域，插件按设计降级。Reports 列出 64 张报表，56 张可走 API，含 partner_performance_by_program 与 partner_performance_by_subid。输出文件与代码里 grep 不到 token 与 SID。

## 待核对

- 有已加入项目后的真实 Actions 行：SubId1 回读、REVERSED 时 Payout 与 IntendedPayout 的取值、ClearedDate 的形状
- Contracts 字段取值：DefaultPayoutRate 是 "8.00" 还是 "8"、Locking.Period 的单位、ValidReferrals 的形状；token 补作用域后核
- csv 退路的表头（后台 Action Listing 导出）
- 按最后更新时间开窗对日常循环的影响：一笔 Action 从 PENDING 变 APPROVED 会再出现一次，对账按 event_id 幂等，应当无害，等真数据核
